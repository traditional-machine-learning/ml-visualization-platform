# 机器学习算法仿真实验与学习平台 · 部署文档

> **阶段说明：** 本文以当前仓库 `master` 分支代码和配置为准。第一阶段《需求规格说明书》仅用于说明项目早期背景与需求来源；第二阶段的开发范围和实现方式有所调整，并未完全按该说明书逐项实施。历史需求不能代替代码验证，也不能据此推断某项功能已经交付。

## 1. 部署形态总览

| 形态 | 适用场景 | 需要准备 |
|---|---|---|
| A. Docker Compose | 本地演示、验收环境；也可作为后续云部署基础（需先做安全调整） | Docker + Docker Compose |
| B. 本地分离启动 | 开发调试 | JDK 17 + Maven + Node 18 + MySQL 8 |
| C. 云服务器（可选部署指南） | 后续自行部署；当前仓库配置不代表已上线公网服务 | Linux 服务器 + Docker + 安全组/防火墙配置 |

本仓库当前提供 Docker Compose 和本地分离启动配置。云服务器部分是可选操作指南，不代表已经完成云端部署。三种形态使用同一份代码和数据库结构，区别在于由容器还是本机提供 MySQL 与静态资源。

| 组件 | 镜像 / 运行方式 | 端口 | 对外 |
|---|---|---|---|
| mysql | `mysql:8.0` | 容器 3306 → 宿主机 3306（当前已映射） | **是，当前配置会发布到宿主机；公网部署前应移除映射** |
| backend | `Dockerfile.backend`：`maven:3.9-eclipse-temurin-17` 构建 → `eclipse-temurin:17-jre` 运行 | 容器 8080 → 宿主机 8080（当前已映射） | **是，当前也发布到宿主机；公网部署建议移除映射，仅由 Nginx 内网转发** |
| frontend | `Dockerfile.frontend`：`node:18-alpine` 构建 → `nginx:alpine` 运行 | 容器 80 → 宿主机 80 | **是，浏览器访问入口** |

## 2. 方式 A：Docker Compose 部署

### 2.1 环境要求

- Docker 20+
- Docker Compose v2（命令为 `docker compose`，不是旧版 `docker-compose`）
- 可用磁盘 ≥ 3GB（镜像 + 数据卷）

### 2.2 启动

```bash
git clone https://github.com/traditional-machine-learning/ml-visualization-platform.git
cd ml-visualization-platform/源代码
docker compose up -d --build
```

首次构建需要拉取 Maven 与 npm 依赖，视网络情况约 5~15 分钟。

### 2.3 启动顺序与依赖

```
mysql（healthcheck 通过）
   └─► backend（depends_on: mysql healthy）
          └─► frontend（depends_on: backend 容器启动）
```

- MySQL 配置了 `healthcheck`，backend 通过 `depends_on.condition: service_healthy` 等待 MySQL 健康后启动；
- frontend 只声明依赖 backend 容器启动，不代表 backend 应用已经通过健康检查（backend/frontend 当前没有 healthcheck）；
- backend 启动时会执行 `schema.sql`（Spring `sql.init`）建表并写预置数据；
- 随后 `DatasetSeedInitializer` 在应用就绪后补齐数据集，这一步失败不影响启动。

### 2.4 验证

```bash
docker compose ps                       # 三个容器应为 running；当前只有 MySQL 配置了 healthcheck
docker compose logs -f backend           # 观察启动日志
curl http://localhost/api/algorithms     # 应返回 success=true 的算法数组
```

浏览器打开 `http://localhost/`。

### 2.5 常用运维命令

| 目的 | 命令 |
|---|---|
| 查看日志 | `docker compose logs -f backend` / `frontend` / `mysql` |
| 重启后端 | `docker compose restart backend` |
| 重新构建后端 | `docker compose up -d --build backend` |
| 停止并保留数据 | `docker compose down` |
| 停止并删除数据卷 | `docker compose down -v` |
| 进入 MySQL | `docker exec -it ml-platform-mysql mysql -uroot -p ml_platform` |

> `docker compose down -v` 会删除数据库卷，下次启动重建表并重新填充数据集——这是「数据乱了」时最干净的恢复手段。

### 2.6 单服务构建（不使用 compose）

```bash
# 后端
docker build -f Dockerfile.backend -t ml-platform-backend:latest ./backend
# 前端
docker build -f Dockerfile.frontend -t ml-platform-frontend:latest ./frontend
```

后端镜像可独立运行，但需要通过网络能访问 MySQL：

```bash
docker run -d --name ml-backend -p 8080:8080 \
  -e SPRING_DATASOURCE_URL="jdbc:mysql://<mysql-host>:3306/ml_platform?useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true" \
  -e SPRING_DATASOURCE_USERNAME=root \
  -e SPRING_DATASOURCE_PASSWORD='<密码>' \
  ml-platform-backend:latest
```

Spring Boot 的宽松绑定会把 `SPRING_DATASOURCE_URL` 映射到 `spring.datasource.url`，因此不必改配置文件。

## 3. 方式 B：本地分离启动

### 3.1 环境要求

| 工具 | 版本 |
|---|---|
| JDK | 17+ |
| Maven | 3.8+ |
| Node.js | 18+（含 npm） |
| MySQL | 8.0+ |

### 3.2 初始化数据库

```bash
mysql -u root -p < backend/src/main/resources/schema.sql
```

脚本内容：

1. `CREATE DATABASE IF NOT EXISTS ml_platform`（utf8mb4 / utf8mb4_0900_ai_ci）；
2. 建 `dataset`、`algorithm`、`training_session` 三张表；
3. 对 `dataset.name` 去重并加唯一索引；
4. 写入 7 个算法、4 个数据集；
5. `UPDATE` 刷新 `svm`、`pca` 的参数定义。

可重复执行，不会产生重复数据。

### 3.3 配置后端

编辑 `backend/src/main/resources/application.yml`，将数据源地址从 Compose 网络中的 `mysql:3306` 改为本机 MySQL 的 `localhost:3306`，并填写本机数据库账号。

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/ml_platform?useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&useUnicode=true&characterEncoding=UTF-8
    username: root
    password: 你的密码
  sql:
    init:
      mode: always        # 启动时执行 schema.sql（可重复执行）

dataset-seed:
  enabled: true
  timeout-seconds: 30
  remote-sources:
    - name: iris
      url: <iris CSV 地址>
      expected-samples: 150
    - name: boston_housing
      url: <boston CSV 地址>
      expected-samples: 506
  synthetic-samples:
    make_classification: 100
    make_blobs: 150

llm:
  endpoint: https://llmapi.paratera.com
  api-key: ${LLM_API_KEY:}   # 推荐的安全配置写法；当前仓库 application.yml 尚未改为环境变量
  model: GLM-4.5-Flash
  max-tokens: 1000
```

### 3.4 启动后端

```bash
cd backend
mvn spring-boot:run
```

或打包后运行：

```bash
mvn clean package -DskipTests
java -jar target/ml-platform-backend-1.0.0.jar
```

后端监听 `8080`。

### 3.5 启动前端

```bash
cd frontend
npm install
npm start
```

`npm start` = `ng serve --proxy-config proxy.conf.json`，会把 `/api` 转发到 `http://localhost:8080`。

前端监听 `4200`，访问 `http://localhost:4200/experiment`。

生产构建：

```bash
npm run build -- --configuration production
# 产物：dist/ml-platform/browser/
```

## 4. 方式 C：云服务器部署（可选指南，尚非已完成部署）

> **重要：** 当前仓库没有可确认的公网部署实例。以下步骤只是后续自行部署的参考。不要不经修改就把当前 `docker-compose.yml` 用于公网环境：它会把 MySQL 3306、后端 8080 和前端 80 都映射到宿主机，而且仓库配置文件含有明文凭据。公网部署前必须轮换凭据、改用环境变量，并移除 MySQL/后端的宿主机端口映射。

### 4.1 服务器建议

| 项 | 建议 |
|---|---|
| CPU / 内存 | 2 核 / 4GB 起 |
| 磁盘 | 40GB |
| 系统 | Ubuntu 20.04+ / CentOS 7+ |
| 安全组 | 放行 80（或自定义端口） |

### 4.2 安装 Docker

**Ubuntu**

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # 重新登录后免 sudo
```

**CentOS**

```bash
sudo yum install -y yum-utils
sudo yum-config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo yum install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo systemctl enable --now docker
```

### 4.3 上传代码并启动

```bash
# 本地
scp -r 源代码 user@<server-ip>:/home/user/ml-platform

# 服务器
cd /home/user/ml-platform
docker compose up -d --build
```

### 4.4 端口与访问

默认把 frontend 的 80 映射到宿主机 80，因此直接访问 `http://<server-ip>/`。

若 80 被占用，改 `docker-compose.yml` 中 frontend 的端口映射（例如 `"8088:80"`），然后：

```bash
docker compose up -d
# 访问 http://<server-ip>:8088/
```

云厂商安全组与系统防火墙都要放行：

```bash
# Ubuntu
sudo ufw allow 80/tcp
# CentOS
sudo firewall-cmd --add-port=80/tcp --permanent && sudo firewall-cmd --reload
```

### 4.5 数据库与后端端口不暴露公网

当前 Compose 文件中 `mysql` 的 `3306:3306` 和 `backend` 的 `8080:8080` 都映射到了宿主机。公网部署前应删除这两个 `ports` 配置，仅保留 frontend 的公开访问端口；Nginx 通过 Docker 内部网络访问 `backend:8080`，backend 再通过内部网络访问 `mysql:3306`。同时确保云安全组和系统防火墙不放行数据库端口。

## 5. 数据集自动填充与代理

### 5.1 机制

`DatasetSeedInitializer`（`ApplicationRunner`）在应用启动后执行：

| 数据集 | 来源 | 目标样本数 |
|---|---|---|
| iris | 远程 CSV | 150 |
| boston_housing | 远程 CSV | 506 |
| make_classification | 程序生成（两簇，seed=42） | 100 |
| make_blobs | 程序生成（三簇，seed=42） | 150 |

**幂等**：只有当表内行数少于目标值时才填充。**安全**：下载/解析/生成任一步失败只 `log.warn`，保留 `schema.sql` 的演示数据，应用照常启动。

### 5.2 需要代理时

优先级：`DATASET_SEED_PROXY` → `HTTPS_PROXY` / `https_proxy` / `HTTP_PROXY` / `http_proxy` → `dataset-seed.proxy-host` + `proxy-port`。

**本地**

```bash
export HTTPS_PROXY=http://127.0.0.1:7890
```

**Docker**：容器内的 `127.0.0.1` 是容器自己，必须用宿主别名：

```yaml
services:
  backend:
    environment:
      HTTPS_PROXY: http://host.docker.internal:7890
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

**完全离线**：直接关闭填充，使用 `schema.sql` 的演示数据：

```yaml
dataset-seed:
  enabled: false
```

### 5.3 验证

```sql
SELECT name, sample_count, feature_count FROM dataset;
```

或看后端日志中的 `[数据集填充]` 行。

## 6. AI 助手配置

### 6.1 配置项

当前仓库 `application.yml` 使用 Paratera 的 OpenAI 兼容接口配置，模型为 `GLM-4.5-Flash`。为避免把密钥写入仓库，建议将配置调整为：

```yaml
llm:
  endpoint: https://llmapi.paratera.com
  api-key: ${LLM_API_KEY:}
  model: GLM-4.5-Flash
  max-tokens: 1000
```

然后在本机 shell 或部署环境中设置 `LLM_API_KEY`。Docker Compose 的 backend 服务也需要显式传入该环境变量：

```yaml
services:
  backend:
    environment:
      LLM_API_KEY: ${LLM_API_KEY}
```

**注意：** 这是一种推荐的安全配置方式。当前仓库的 `application.yml` 仍含有明文 API Key，且现有 Compose 配置尚未传入 `LLM_API_KEY`；仅在终端设置环境变量不会自动覆盖当前 YAML 中的字面量配置。需要先修改配置文件再使用环境变量方式。
### 6.2 安全提醒（务必执行）

当前公开仓库的 `application.yml` 和 `docker-compose.yml` 中存在明文数据库凭据及大模型 API Key。本文不复制具体值。由于这些配置已经进入公开仓库，应视为已暴露：请尽快轮换数据库凭据和 API Key，并将配置改为环境变量或密钥管理。仅删除当前文件中的明文值不能清除 Git 历史中的旧值。

1. **不要把真实 Key 提交到仓库**。`application.yml` 与 `docker-compose.yml` 会被 git 跟踪，一旦推送即视为泄露。
2. 若历史上提交过 Key：立刻到控制台**吊销并重建**，再改成环境变量；仅删文件里的字符串**不够**，git 历史仍在。
3. 仓库根目录 `.gitignore` 已忽略 `.env` / `.env.local`；密钥可通过本地环境变量或受忽略保护的本地文件提供，不要提交本地密钥文件。

### 6.3 未配置时的行为

AI 面板仍可输入提问，但返回：

```text
AI API key not configured. Please set LLM_API_KEY environment variable.
```

不影响其他功能。

## 7. 数据库维护

### 7.1 备份

```bash
docker exec ml-platform-mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" ml_platform' > backup.sql
```

本地 MySQL：

```bash
mysqldump -u root -p ml_platform > backup.sql
```

### 7.2 恢复

```bash
docker exec -i ml-platform-mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ml_platform' < backup.sql
```

### 7.3 清理训练会话

`training_session` 会随训练不断累积（每次「开始」新增一行），演示环境可定期清理：

```sql
-- 只保留最近 100 条
DELETE FROM training_session
WHERE id NOT IN (SELECT id FROM (SELECT id FROM training_session ORDER BY id DESC LIMIT 100) t);
```

### 7.4 重置数据集

```sql
-- 让填充器下次启动重新下载/生成（保留元数据）
UPDATE dataset SET data_content = JSON_ARRAY(), sample_count = 0;
```

然后重启后端。

## 8. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `dockerDesktopLinuxEngine` 连接失败 | Docker Desktop 未启动 | 启动后等状态为 Running |
| `port is already allocated`（3306） | 本机 MySQL 占用 | 停本机 MySQL 或改用方式 B |
| `port is already allocated`（80） | 本机 Nginx/Apache 占用 | 改映射端口 |
| backend 反复重启 | 数据库连不上 / 密码错 | `docker compose logs backend` 看 `Communications link failure` |
| 前端接口 404 / 返回 HTML | 请求打到了前端路由 | 确认走 `/api` 前缀且 Nginx/proxy 配置生效 |
| 页面提示「API 不可用」 | 后端未起或接口报错 | 打开浏览器 Network 看具体失败请求 |
| 数据集只有几条 | 远程 CSV 下载失败 | 查 `[数据集填充]` 日志；配代理或 `enabled: false` |
| 中文乱码 | 连接未指定字符集 | URL 加 `useUnicode=true&characterEncoding=UTF-8`，库用 utf8mb4 |
| 训练卡在 0 步 | 未选算法/数据集；后端 500 | 看后端日志与 `training_session` 是否可写 |
| 图表尺寸异常 / 空白 | 路由保活后容器尺寸失效 | 回到页面应自动 `resize`；仍异常则刷新 |
| AI 返回「key not configured」 | 未配置环境变量 | 按第 6 节配置 |

## 9. 升级与回滚

```bash
# 拉取新代码
git pull

# 只重建有变更的服务
docker compose up -d --build backend
docker compose up -d --build frontend

# 若数据库结构有变更，先备份再重建
docker exec ml-platform-mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" ml_platform' > backup_$(date +%F).sql
docker compose down
docker compose up -d --build
```

`schema.sql` 采用「可重复执行」写法，多数结构变更可以直接靠重跑脚本完成；涉及列删除/改名的变更仍需手工迁移。
