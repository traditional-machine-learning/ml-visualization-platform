# ML 可视化平台 · 设计模式分析

> 对照模板库：`Desktop/设计模式源代码/designpattern`（9 个模式目录）与 `Combat`（战斗机对战示例）  
> 分析对象：`work/ml-visualization-platform/源代码`（Spring Boot + MyBatis + Angular）  
> 说明：本文只统计**代码里真实存在**的落地，不为了凑数硬套；凡是「框架内置」「仅具雏形」「可重构」的，都单独标注。

## 一、总览：模板库 9 个模式在本项目的命中情况

| 模板目录                    | 模式   | 命中度          | 本项目落地位置                                                                                                    |
| ----------------------- | ---- | ------------ | ---------------------------------------------------------------------------------------------------------- |
| `singleton`             | 单例   | ★★★ 全覆盖      | Spring `@Service/@RestController` 默认单例；Angular `providedIn:'root'`；`DatasetSeedInitializer` 懒汉式 HttpClient |
| `simpleFactory`         | 简单工厂 | ★★★ 业务核心     | `TrainingSimulationService` 按算法名分派；`ApiResponse.success/error` 静态工厂；`fillSynthetic` 按数据集名分派                |
| `adapter`               | 适配器  | ★★★          | `DatasetService.convertToDTO`、`AiAssistantService.extractContent`、`@ConfigurationProperties` 配置绑定          |
| `observer`              | 观察者  | ★★★ 框架级      | RxJS `Observable` + `router.events.subscribe`；组件订阅 `ApiService`                                            |
| `proxy`                 | 代理   | ★★★          | Nginx `proxy_pass`、`proxy.conf.json`、`ApiService` 远程代理                                                     |
| `templateMethod`        | 模板方法 | ★★☆          | `DatasetSeedInitializer.run` 骨架、`stepTraining` 固定流程、Angular 生命周期钩子                                         |
| `factoryMethod`         | 工厂方法 | ★☆☆ 框架级      | `@Bean` 声明、Angular DI `useClass` 提供实现                                                                      |
| `ChainofResponsibility` | 责任链  | ★☆☆ 框架级 + 变体 | Servlet Filter / `HandlerExceptionResolver` 链；`resolveProxy` 优先级候选链                                        |
| `abstractFactory`       | 抽象工厂 | — 未使用        | 项目无「产品族」维度，不建议硬套（见 §3.3）                                                                                   |

模板库之外，项目还自带 4 个模式（详见 §4）：**备忘录**（训练快照）、**门面**（大服务收口）、**仓储**（MyBatis Mapper）、**状态**（训练状态机）。

依赖注入本身就是「设计模式容器」：`@Service` 是单例、`@Mapper` 是仓储、`@ConfigurationProperties` 是适配器、`RouteReuseStrategy` 是策略——Spring 与 Angular 把这些模式的注册工作做掉了，业务代码只需声明。

## 二、★★★ 业务层自建的模式

### 2.1 单例模式（模板 `singleton`）

**意图**：全局唯一实例，避免重复创建昂贵对象，并提供统一访问点。

**角色映射**

| 模板角色                          | 项目对应                                           |
| ----------------------------- | ---------------------------------------------- |
| `LazySingleton.getInstance()` | `DatasetSeedInitializer.httpClient()`          |
| `EagerSingleton`（饿汉）          | Spring `@Service` 容器启动即建实例                     |
| 客户端调用                         | `AlgorithmController` 构造器注入 `AlgorithmService` |

**模板写法（懒汉）**

```java
public class LazySingleton {
    private static LazySingleton instance;
    private LazySingleton() {}
    public synchronized static LazySingleton getInstance() {
        if (instance == null) { instance = new LazySingleton(); }
        return instance;
    }
}
```

**项目落地**：`DatasetSeedInitializer.java:325-338` —— 双重判断的懒加载，只是把 `static` 换成了 Bean 字段（Spring Bean 自身已是单例，所以无需 `synchronized`）：

```java
private HttpClient httpClient;

private HttpClient httpClient() {
    if (httpClient == null) {                       // ← 懒汉式判断
        HttpClient.Builder builder = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(properties.getTimeoutSeconds()));
        InetSocketAddress proxy = resolveProxy();
        if (proxy != null) { builder.proxy(ProxySelector.of(proxy)); }
        httpClient = builder.build();               // ← 首次访问才创建
    }
    return httpClient;
}
```

另外三处「天然单例」：

- `@Service public class AlgorithmService`（`AlgorithmService.java:14`）—— Spring 默认 scope 为 singleton，所有 Controller 共享同一实例，因此**服务层禁止持有请求级可变状态**。
- `@Injectable({ providedIn: 'root' }) export class ApiService`（`api.service.ts:14-17`）—— Angular 根注入器单例，等价于前端全局唯一后端入口。
- `@Injectable({ providedIn: 'root' }) ExperimentContextService`（`experiment-context.service.ts:4`）—— 靠单例身份在组件树之间共享训练上下文。

> **对照结论**：模板用「私有构造 + 静态方法」保证唯一；本项目用「容器托管」保证唯一。手段不同，约束相同 —— 都不能 `new`，都要求无状态。

### 2.2 简单工厂（模板 `simpleFactory`）

**意图**：把「选择哪个实现」的 switch/if 收敛到一个创建点，调用方只传类型。

**角色映射**

| 模板角色                             | 项目对应                                                                    |
| -------------------------------- | ----------------------------------------------------------------------- |
| `PenFactory.createPen(PenType)`  | `TrainingSimulationService.trainAlgorithmStep(...)`                     |
| `PenType` 枚举                     | 数据库字段 `algorithm.name` / `algorithm.type`                               |
| `Pen` / `Pencil` / `FountainPen` | `trainLinearRegression` / `trainLogisticRegression` / `trainKMeans` / … |

**模板写法**

```java
public class PenFactory {
    public enum PenType { PENCIL, FOUNTAIN_PEN }
    public static Pen createPen(PenType type) {
        switch (type) {
            case PENCIL:       return new Pencil();
            case FOUNTAIN_PEN: return new FountainPen();
            default: throw new IllegalArgumentException("Unknown pen type");
        }
    }
}
```

**项目落地**：`TrainingSimulationService.java:398-428` —— 结构完全同构，只是 `switch` 被写成了 `if` 链，枚举换成了字符串键：

```java
private StepResult trainAlgorithmStep(Algorithm algorithm, Dataset dataset,
                                      String parameters, ModelData modelData) {
    String name = algorithm.getName() == null ? "" : algorithm.getName();
    String type = algorithm.getType() == null ? "" : algorithm.getType();

    if ("linear_regression".equals(name))            return trainLinearRegression(dataset, parameters, modelData);
    if ("logistic_regression".equals(name))          return trainLogisticRegression(dataset, parameters, modelData);
    if ("kmeans".equals(name) || "clustering".equals(type)) return trainKMeans(dataset, parameters, modelData);
    if ("decision_tree".equals(name))                return trainDecisionTree(dataset, parameters, modelData);
    if ("svm".equals(name))                          return trainSvm(dataset, parameters, modelData);
    if ("classification".equals(type))               return trainLogisticRegression(dataset, parameters, modelData);
    if ("regression".equals(type))                   return trainLinearRegression(dataset, parameters, modelData);
    return evaluateCurrentState(algorithm, dataset, parameters, modelData);   // ← 兜底分支
}
```

同一个类里还有两处同款分派（共 3 个创建点，属于「同一个工厂被复制了三份」）：

- `initializeModelData`（`:353-386`）——按算法名创建初始模型数据结构；
- `evaluateCurrentState`（`:430-451`）——按算法名选择评估方式。

**另外两处简单工厂**

| 位置                                    | 产品                           | 形态                                                      |
| ------------------------------------- | ---------------------------- | ------------------------------------------------------- |
| `ApiResponse.java:8-29`               | `ApiResponse<T>` 成功/失败两种结果对象 | 静态工厂方法 `success()` / `error()`，比 `new` + setter 更表达意图   |
| `DatasetSeedInitializer.java:200-208` | 合成数据集行列表                     | `if ("make_classification") … else if ("make_blobs") …` |

> **对照结论**：与 `PenFactory` 同构，但存在两个工程质量问题：  
> ① 键是裸字符串（`"svm"`），编译器无法校验拼写，改名靠全局搜索；  
> ② 三个分派点各写一遍，新增算法必须同步改 3 处，漏一处就出现「能训练但不能评估」。  
> 这正是 §5「策略 + 注册表」重构要解决的问题。

### 2.3 适配器（模板 `adapter`）

**意图**：把不兼容的接口/数据形状转换成调用方期望的接口，让老代码或第三方服务能直接接入。

**角色映射**

| 模板角色                   | 项目对应                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| `Voltage`（目标接口）        | `AlgorithmDTO` / `DatasetDTO` / `AiAssistantResponse`                                     |
| `SpecialVoltage`（被适配者） | `Algorithm` 实体、OpenAI 响应 `Map`、YAML 配置项                                                   |
| `VoltageAdapter`（适配器）  | `DatasetService.convertToDTO`、`AiAssistantService.extractContent`、`DatasetSeedProperties` |

**模板写法**

```java
public class VoltageAdapter implements Voltage {
    private SpecialVoltage specialVoltage;
    public VoltageAdapter(SpecialVoltage specialVoltage) { this.specialVoltage = specialVoltage; }
    @Override public void supplyVoltage() { specialVoltage.provideSpecialVoltage(); }
}
```

**项目落地 1：实体 → DTO（持久层形状适配成前端形状）**  
`DatasetService.java:65-84`

```java
private DatasetDTO convertToDTO(Dataset dataset, boolean withDimensionValues) {
    DatasetDTO dto = new DatasetDTO();
    dto.setId(dataset.getId());
    dto.setName(dataset.getName());
    // …
    List<DatasetDTO.FeatureInfo> features = parseFeatures(dataset.getFeatures());  // JSON 字符串 → 对象
    Projection projection = buildProjection(features);                             // 维度裁剪 → x/y
    dto.setFeatures(projectFeatures(features, projection));
    dto.setDataPoints(projectDataPoints(parseRows(dataset.getDataContent()), projection,
            withDimensionValues ? features : null));                               // 行 MAP → DataPoint
    return dto;
}
```

这里适配了 3 种「不兼容」：JSON 文本 ↔ 强类型对象、任意维度 ↔ 固定 `x/y` 画布坐标、单条记录 ↔ 两种视图（列表精简版 / 详情全维度版，由 `withDimensionValues` 开关控制）。

**项目落地 2：第三方响应 → 内部对象**  
`AiAssistantService.java:111-121` —— OpenAI 的 `choices[0].message.content` 嵌套 Map 被压平成 `String`：

```java
private String extractContent(Map response) {
    List choices = (List) response.get("choices");
    if (choices != null && !choices.isEmpty()) {
        Map choice = (Map) choices.get(0);
        Map message = (Map) choice.get("message");
        if (message != null) { return (String) message.get("content"); }
    }
    return "No response received from AI.";
}
```

反向的适配同样存在：`buildUserPrompt`（`:75-109`）把内部的算法/数据集/训练指标对象拼装成 LLM 需要的自然语言 prompt —— 内部模型充当了「被适配者」。

**项目落地 3：配置 → 对象**  
`DatasetSeedProperties.java:17-20`，`@ConfigurationProperties(prefix = "dataset-seed")` 把 `application.yml` 的层级键绑定到嵌套 Java 对象（`remoteSources`、`syntheticSamples`），Spring 的 Binder 就是这层适配器，业务代码只看到 `properties.getRemoteSources()`。

> **对照结论**：三处都是「接口形态转换」，但项目没有抽出统一的 `Adapter` 接口 —— 对 DTO 场景是合理的（多一层抽象反而增加跳转成本），对第三方 API 场景（AI 服务）则建议补一层 `LlmClient` 接口，以便替换 OpenAI / 本地模型。

### 2.4 观察者（模板 `observer`）

**意图**：主题状态变化时，一次性通知所有已注册观察者，双方无需互相持有具体类型。

**角色映射**

| 模板角色                       | 项目对应                                                |
| -------------------------- | --------------------------------------------------- |
| `Subject`（注册/注销/通知）        | RxJS `Observable`（`router.events`、`http.get()` 返回值） |
| `WeatherStation`（具体主题）     | Angular `Router` 事件流、`ApiService` 的 HTTP 流          |
| `Observer.update(...)`     | 组件 `subscribe(next)` 回调                             |
| `CurrentConditionsDisplay` | `ExperimentComponent`                               |

**模板写法**

```java
public void notifyObservers() {
    for (Observer observer : observers) { observer.update(temperature, humidity, pressure); }
}
```

**项目落地：`experiment.component.ts:68-93`**

```typescript
this.navigationSub = this.router.events
  .pipe(filter((event): event is NavigationEnd => event instanceof NavigationEnd))
  .subscribe((event) => {                              // ← Observer.update
    if (event.urlAfterRedirects.split('?')[0].startsWith('/experiment')) {
      setTimeout(() => window.dispatchEvent(new Event('resize')), 60);   // 重算 ECharts 尺寸
    }
  });

ngOnDestroy(): void {
  this.clearTrainingTimer();
  this.navigationSub?.unsubscribe();    // ← removeObserver，等价于模板的 observers.remove(o)
  this.navigationSub = null;
}
```

同一个模式在数据链路上重复出现：`ApiService.getDatasets()` 返回 `Observable`（`api.service.ts:23-25`），组件订阅后渲染；`TrainingSimulationResponse` 每步返回也是流式推送语义。

> **对照结论**：模板手写 `ArrayList<Observer>` + 遍历通知；项目用 RxJS 把「注册/注销/通知/背压/取消」全部内建。**关键差异**是项目显式在 `ngOnDestroy` 里 `unsubscribe` —— Angular 的组件被 `RouteReuseStrategy` 保活（见 §2.5）时不会自动销毁，忘记取消订阅就是内存泄漏 + 重复回调。

### 2.5 代理（模板 `proxy`）

**意图**：为真实对象提供同接口的替身，在调用前后插入额外逻辑（转发、缓存、访问控制）。

**角色映射**

| 模板角色                  | 项目对应                                |
| --------------------- | ----------------------------------- |
| `HouseRental`（公共接口）   | 后端 `/api/**` 契约、`ApiResponse<T>` 外壳 |
| `HouseOwner`（真实对象）    | `http://backend:8080` 上的 Spring 控制器 |
| `RealEstateAgent`（代理） | Nginx `location /api/`、`ApiService` |

**模板写法**

```java
public void rent() {
    if (houseOwner == null) { houseOwner = new HouseOwner(property); }   // 按需创建真实对象
    arrangeViewing();                                                    // 附加动作
    houseOwner.rent();                                                   // 转发
}
```


**项目落地**

| 层 | 位置 | 代理类型 | 附加逻辑 |
|---|---|---|---|
| 部署 | `frontend/nginx.conf:11-17` | 反向代理 | `proxy_pass http://backend:8080/api/`，顺带解决容器内服务发现与跨域 |
| 开发 | `frontend/proxy.conf.json` | 开发代理 | 把 `localhost:4200/api` 转到 `localhost:8080`，前端代码零改动 |
| 代码 | `services/api.service.ts:14-116` | 远程代理 | 统一 `baseUrl`（来自 `environment`）、统一泛型 `ApiResponse<T>`、参数序列化（`JSON.stringify(parameters)`） |

`ApiService` 的代理价值在签名上体现得最清楚 —— 组件只需 `this.apiService.trainStep(id, sessionId, datasetId, params)`，不必关心 URL 拼接、请求体结构、响应解包：

```typescript
trainStep(algorithmId: number, sessionId: number, datasetId: number, parameters: any)
  : Observable<ApiResponse<TrainingSimulationResponse>> {
  return this.http.post<ApiResponse<TrainingSimulationResponse>>(
    `${this.baseUrl}/algorithms/${algorithmId}/step`,
    { sessionId, datasetId, parameters: JSON.stringify(parameters) });
}
```

> **对照结论**：模板的代理是「同接口 + 手工转发」；项目的代理是「网络层转发（Nginx）+ 客户端 SDK 封装（ApiService）」两层叠加。若将来要加鉴权、重试、错误提示，正确位置是 Angular `HttpInterceptor`（一条链上的代理），而不是在每个 Service 里重复写。

### 2.6 模板方法（模板 `templateMethod`）

**意图**：父类固定算法骨架（`final` 方法），把可变步骤留给子类实现，保证流程顺序不可篡改。

**角色映射**

| 模板角色 | 项目对应 |
|---|---|
| `AbstractClass.TemplateMethod()`（final 骨架） | `DatasetSeedInitializer.run()`；`TrainingSimulationService.stepTraining()` |
| `TakeANumber/QueueUp/Evaluate`（固定步骤） | 「查存在性 → 判是否已满足 → 记日志 → 保存」 |
| `Business()`（抽象变化点） | `fillFromRemote` / `fillSynthetic`；`trainAlgorithmStep` |

**模板写法**

```java
public abstract class AbstractClass {
    public final void TemplateMethod() {
        TakeANumber(); QueueUp(); Business(); Evaluate();
    }
    protected abstract void Business();
}
```

**项目落地 1：数据集填充流程（`DatasetSeedInitializer.java:58-103`）**

骨架固定，只有「获取数据」这一步可变：

```java
public void run(ApplicationArguments args) {              // ← TemplateMethod，不允许子类改写顺序
    for (RemoteSource source : properties.getRemoteSources()) { fillFromRemote(source); }
    for (Map.Entry<String, Integer> e : properties.getSyntheticSamples().entrySet()) {
        fillSynthetic(e.getKey(), e.getValue());
    }
}

    saveRows(dataset, parseCsv(csv, ...), name, "下载");   // 固定步骤：统一落库
}

private void fillSynthetic(String name, int samples) {    // ← 变化点 B：合成数据 = 随机生成
    ...
    saveRows(dataset, rows, name, "生成");                 // 同一个收尾步骤
}
```

两个变化点最终都汇入同一个 `saveRows`（`:254-263`，统一更新 `data_content`/`sample_count`/`feature_count`），这就是模板方法的核心收益：**收尾逻辑只有一份**。

**项目落地 2：单步训练流程（`TrainingSimulationService.java:65-93`）**


`startTraining`（`:42-63`）、`pauseTraining`（`:95-116`）共用「取会话 → 校验 → 组装响应 → 持久化」这条骨架，只是变化点不同。

**项目落地 3：框架级模板方法**`MLPlatformApplication.java:22` 的 `CommandLineRunner`、`DatasetSeedInitializer` 的 `ApplicationRunner`，以及 Angular 的 `ngOnInit/ngOnChanges/ngOnDestroy` —— 骨架由框架定义（调用时机、顺序不可改），业务只填方法体。

> **对照结论**：模板库用继承（`abstract class`）实现；项目里 `TrainingSimulationService` 把变化点收敛成私有方法而非子类，属于**模板方法的「组合」变体**（无需继承、无 `final` 约束）。代价是「顺序」只靠代码阅读保证，没有 `final` 的编译期保护。

## 三、框架级使用 / 未使用

### 3.1 工厂方法（模板 `factoryMethod`）—— 交给容器

**意图**：定义创建接口，由子类（具体工厂）决定实例化哪一个产品。

**模板写法**

```java
public abstract class PenFactory { public abstract Pen createPen(); }
```

**项目对应**

| 位置 | 形式 |
|---|---|
| `app.module.ts:78-80` | `{ provide: RouteReuseStrategy, useClass: KeepAliveRouteReuseStrategy }` —— 抽象类 `RouteReuseStrategy` 是产品接口，`useClass` 指定具体实现，Angular 注入器充当具体工厂 |
| `MLPlatformApplication.java:22-53` | `@Bean CommandLineRunner ensureAlgorithms(...)` —— 用工厂方法向容器注册产品，调用方不 `new` |
| `AiAssistantService.java:23-32` | 构造器内 `WebClient.builder()…build()` —— 建造者 + 工厂组合创建不可变客户端 |

> **结论**：项目没有自建 `XxxFactory` 抽象类。对当前规模是正确的取舍 —— Spring / Angular 容器已经是工厂，再包一层 `AlgorithmServiceFactory` 只是给容器套壳。

### 3.2 责任链（模板 `ChainofResponsibility`）—— 只有框架链

**模板结构**：`SensitiveWordFilter.setSuccessor(next)` 串成链，逐个 `doFilter`。

**项目现状**

| 位置 | 说明 |
|---|---|
| Spring MVC `FilterChain` → `DispatcherServlet` → `HandlerInterceptor` → `Controller` | 框架内置链，项目通过 `WebConfig implements WebMvcConfigurer`（`WebConfig.java:8-18`）预留了插入拦截器的位置 |
| `GlobalExceptionHandler`（`config/GlobalExceptionHandler.java`） | `@RestControllerAdvice` 是 `HandlerExceptionResolver` 链上的一环：`ExceptionHandler` 按「异常类型最具体优先」逐级匹配，`IllegalArgumentException → 400`、`Exception → 500` |
| `DatasetSeedInitializer.resolveProxy()`（`:345-358`） | 唯一自建的「候选链」：`DATASET_SEED_PROXY → HTTPS_PROXY → http_proxy → 配置文件`，用 `firstNonBlank(...)` 顺序取值，命中即返回 |

```java
String fromEnv = firstNonBlank(
        System.getenv("DATASET_SEED_PROXY"),
        System.getenv("HTTPS_PROXY"), System.getenv("https_proxy"),
        System.getenv("HTTP_PROXY"), System.getenv("http_proxy"));
if (fromEnv != null && !fromEnv.isBlank()) { return parseProxyUri(fromEnv); }
```

> **结论**：这是参数化的「候选查找」，没有 `successor` 指针与 `Handler` 抽象，属于责任链的**退化形态**。若要把代理规则扩展成「多条规则依次尝试」，才值得抽象成真正的链。

### 3.3 抽象工厂（模板 `abstractFactory`）—— 未使用，且不建议加

**判断依据**：抽象工厂的价值在于「一个工厂负责同一产品族的多条产品线」，例如模板里 `FountainPenFactory` 同时产 `FountainPen` + `InkBottle`，`PencilFactory` 同时产 `Pencil` + `PencilBox`。

本项目只有**一个变化维度**（算法种类）：每个算法对应一个「训练 + 评估 + 初始化」组合，它们属于同一条产品线的不同方法，而不是互相配套的产品族。强行引入抽象工厂只会得到：

```java
// 反面示例：产品族成员之间毫无配套关系，接口纯属噪音
public interface AlgorithmKitFactory {
    StepTrainer createTrainer();
    StepEvaluator createEvaluator();
    ModelInitializer createInitializer();
}
```

**真正的痛点不在「产品族」，而在「分派散落三处」** —— 用 §5 的策略 + 注册表解决即可。

## 四、模板库之外，项目自带的 4 个模式

### 4.1 备忘录（Memento）—— 训练快照与断点续训

这是本项目**最有辨识度**的一个模式，模板库里没有对应目录。

**角色映射**

| 备忘录角色 | 项目对应 |
|---|---|
| `Memento`（快照） | `TrainingSession.modelData` + `TrainingSession.metrics`（JSON 文本，`model/TrainingSession.java:13-14`） |
| `Originator`（原发器，负责存档/读档） | `TrainingSimulationService`（`toJson` / `fromJson`） |
| `Caretaker`（管理者） | `TrainingSessionRepository`（MySQL 持久化，跨进程、跨重启） |

**存档**（`stepTraining` 末尾，`:88-90`）

```java
session.setMetrics(toJson(response.getMetrics()));        // 快照：指标序列
session.setModelData(toJson(response.getModelData()));    // 快照：模型参数/质心/边界
trainingSessionRepository.update(session);
```

**读档**（`readOrInitializeModelData`，`:388-396`）

```java
if (session.getModelData() != null && !session.getModelData().isBlank()) {
    return fromJson(session.getModelData(), ModelData.class);   // 有快照就恢复
}
return initializeModelData(algorithm, dataset, session.getParameters());  // 没有就重建
```

**为什么值得单列**：`pauseTraining` → 前端停止 `setInterval` → 用户离开页面 → 数小时后 `onResumeTraining`，模型权重、质心位置、决策边界全部从数据库快照还原，训练步数从 `currentStep` 继续。没有备忘录模式，这套「暂停/恢复」根本无法实现 —— 服务端每次请求都是无状态的。

同一个思想在前端以「组件实例缓存」的形式再现：`KeepAliveRouteReuseStrategy`（`routing/keep-alive-route-reuse.strategy.ts:14-49`）把 `experiment`、`learn` 两个路由的 `DetachedRouteHandle` 存进 `Map`，返回时 `retrieve` 出原实例，训练定时器与作答状态因此不被销毁 —— 缓存的是**内存对象快照**，而非 JSON。

### 4.2 门面（Facade）—— 大服务收口

`TrainingSimulationService` 共 1822 行、40+ 私有方法，对外只暴露 8 个方法（`startTraining` / `stepTraining` / `pauseTraining` / `getModelData` / `getMetrics` / `startPca` / `startRandomForest` / `simulateFeatureSelection`）。控制器只看到一个干净的 API：

```java
@PostMapping("/{id}/train")
public ApiResponse<TrainingSimulationResponse> startTraining(@PathVariable Long id,
                                                             @RequestBody TrainingRequest request) {
    return ApiResponse.success(trainingSimulationService.startTraining(
            id, request.getDatasetId(), request.getParameters()));
}
```

门面内部的隐藏复杂度包括：JSON 解析、特征投影、数值归一化、归一化参数、梯度下降、K-Means 迭代、PCA 特征分解、决策树贪心分裂、SVM 核函数、指标插值、会话持久化。

同类门面还有 `ApiService`（13 个端点收口成 1 个类，前端 9 个组件共用一个注入点）。

> **风险提示**：门面越大，越容易变成「上帝类」。`TrainingSimulationService` 已经同时承担训练、评估、初始化、JSON 序列化、特征解析 5 类职责，建议按 §5 拆分。

### 4.3 仓储（Repository）—— MyBatis Mapper 隔离 SQL

`repository/AlgorithmRepository.java:12-35`：接口 + 注解 SQL，业务层只看到方法名，不接触 `SELECT`：

```java
@Mapper
public interface AlgorithmRepository {
    @Select("SELECT * FROM algorithm WHERE name = #{name}")
    Algorithm findByName(String name);
    @Insert("INSERT INTO algorithm (...) VALUES (...)")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(Algorithm algorithm);
}
```

这是分层架构的支点：`AlgorithmService` 依赖接口而非数据库，`@MapperScan("com.mlplatform.repository")`（`MLPlatformApplication.java:15`）负责扫描注册 —— 仓储的实现类由 MyBatis 在运行时通过动态代理生成，又是一次「代理模式」的应用。

### 4.4 状态（State）—— 训练状态机的轻量实现

`TrainingSession.status` 的取值 `training` / `paused` / `completed` 与迁移规则写在服务层：

```java
session.setStatus(nextStep >= totalSteps ? "completed" : "training");   // stepTraining:85
session.setStatus(currentStep >= totalSteps ? "completed" : "paused");  // pauseTraining:105
```

前端对应 `normalizeStatus`（`experiment.component.ts:527`）把字符串收敛为 `TrainingState['status']` 联合类型，编译期即可防止非法状态。

> **结论**：这是「状态字段 + 条件表达式」，不是 GoF 状态模式（没有 `State` 抽象类与状态对象）。当前只有 3 个状态、迁移规则 2 条，用状态类属于过度设计；**当前实现是合适的**，但状态一旦超过 5 个或出现「暂停中取消」「失败重试」等分支，就该重构为状态对象。

## 五、重构建议：把 3 处分派收成一个策略注册表

**问题定位**（均在同一文件 `TrainingSimulationService.java`）

| 行号 | 方法 | 职责 |
|---|---|---|
| `353-386` | `initializeModelData` | 按算法名创建初始模型 |
| `398-428` | `trainAlgorithmStep` | 按算法名执行一步训练 |
| `430-451` | `evaluateCurrentState` | 按算法名计算指标 |

新增一个算法（例如 `xgboost`）需要改 3 处 `if`，且 `getLossLabel`（`:1536-1551`）里还有第 4 处硬编码的损失名映射。这是典型的「开闭原则」违背：**对扩展不开放，必须改源码**。

**重构方案：策略模式 + 注册表工厂**，形态与模板库 `simpleFactory/PenFactory` 完全一致 —— 区别只是 `Pen` 换成了 `TrainStepStrategy`，`switch` 换成了 `Map` 查表：


```java
// 1) 策略接口：一个算法 = 一个策略实现
public interface TrainStepStrategy {
    String name();                                             // 唯一键，替代裸字符串
    default String lossLabel() { return "Loss"; }
    ModelData initialize(Dataset dataset, String parameters);
    StepResult trainStep(Dataset dataset, String parameters, ModelData modelData);
    StepResult evaluate(Dataset dataset, String parameters, ModelData modelData);
}

// 2) 具体策略：把现有私有方法搬进独立类
@Component
public class KMeansTrainStrategy implements TrainStepStrategy {
    public String name() { return "kmeans"; }
    public String lossLabel() { return "Inertia"; }
    public ModelData initialize(...) { /* 原 initializeModelData 的 kmeans 分支 */ }
    public StepResult trainStep(...) { /* 原 trainKMeans */ }
    public StepResult evaluate(...) { /* 原 evaluateKMeans */ }
}

// 3) 注册表工厂：构造器注入所有策略，按名索引
@Component
public class TrainStepStrategyRegistry {
    private final Map<String, TrainStepStrategy> strategies;

    public TrainStepStrategyRegistry(List<TrainStepStrategy> all) {
        this.strategies = all.stream().collect(Collectors.toMap(TrainStepStrategy::name, s -> s));
    }

    public TrainStepStrategy resolve(Algorithm algorithm) {
        TrainStepStrategy s = strategies.get(algorithm.getName());
        if (s == null) { s = strategies.get(algorithm.getType()); }   // 兼容按 type 归类
        if (s == null) { throw new IllegalArgumentException("No strategy for: " + algorithm.getName()); }
        return s;
    }
}
```

调用方随之退化为一行：

```java
StepResult result = registry.resolve(algorithm).trainStep(dataset, parameters, modelData);
```

**收益对照**

| 维度 | 现状 | 重构后 |
|---|---|---|
| 新增算法 | 改 4 处 `if` + 重启验证 | 新增 1 个 `@Component` 类，容器自动注册 |
| 算法名拼写 | 字符串散落各处 | 集中在 `name()` 一个方法 |
| 单元测试 | 只能整体测 1822 行服务 | 单测单个策略，无需数据库 |
| 类体积 | 1822 行 | 主服务降到约 300 行编排逻辑 |

**不建议动的部分**：`ApiResponse` 静态工厂、`@Mapper` 仓储、`RouteReuseStrategy` 注入 —— 这些已经是「容器即工厂」「接口即策略」的标准形态，再抽象只会增加跳转层级。
