> 说明：本文只统计**代码里真实存在**的落地，不为了凑数硬套；凡是「框架内置」「仅具雏形」「可重构」的，都单独标注。

## 一、总览：模板库 9 个模式与本项目代码结构的对应情况

| 模板目录 | 模式 | 本项目中的对应结构 | 认定边界 |
| --- | --- | --- | --- |
| `singleton` | 单例 | Spring `@Service/@RestController` 默认 singleton scope；Angular `providedIn:'root'` | 由框架容器管理生命周期，不是手写私有构造器式单例 |
| `simpleFactory` | 简单工厂 | `ApiResponse.success/error` 静态工厂方法；算法名分派与合成数据分派 | `TrainingSimulationService` 的 `if` 分支主要是算法分派，并不创建多态算法对象，属于简单工厂式结构而非严格 GoF 工厂 |
| `adapter` | 适配器 | `DatasetService.convertToDTO`、`AiAssistantService.extractContent`、`projectModel` | 有明确的数据形状/接口转换，可作为较强的适配器实例 |
| `observer` | 观察者 | RxJS `Observable`、`router.events.subscribe`、组件订阅 `ApiService` | 主要由 Angular/RxJS 提供观察者机制，项目没有自建完整 Observer 类体系 |
| `proxy` | 代理 | Nginx `proxy_pass`、开发代理配置、MyBatis `@Mapper` 动态代理 | 属于网络与持久层基础设施；`ApiService` 是统一 HTTP 客户端封装，不单独认定为 GoF 代理 |
| `templateMethod` | 模板方法式流程 | `DatasetSeedInitializer.run`、`stepTraining` 等固定流程 | 体现固定骨架与变化步骤，但没有经典 GoF 模板方法所要求的抽象父类/子类覆写 |
| `factoryMethod` | 框架对象创建 | Spring `@Bean`、Angular DI `useClass` | 属于框架容器的对象创建/注入机制，不计为项目自建的 GoF 工厂方法 |
| `ChainofResponsibility` | 框架处理链 | Spring MVC/异常解析框架链 | 由框架内部提供；项目自有的代理环境变量优先级只是候选查找，不认定为业务责任链 |
| `abstractFactory` | 抽象工厂 | 未发现 | 当前没有需要成族创建的相关产品，不建议为了模式数量而添加 |

模板库之外，代码还存在若干**模式相似结构**（详见 §4）：训练快照持久化（备忘录式）、统一服务入口（外观式）、MyBatis Mapper 数据访问抽象（Repository-like）、训练状态字段与迁移（状态机）、路由实例/投影结果缓存（缓存与复用）。这些结构不都等同于严格的 GoF 模式。

框架依赖注入会自动管理对象创建与生命周期，但不应把每一种容器机制都直接算作项目实现了相应 GoF 模式。本文将业务代码、自带结构和框架机制分开说明。

## 二、较明确的模式实现与模式相似结构

### 2.1 容器管理的单例生命周期（模板 `singleton`）

**意图**：全局唯一实例，避免重复创建昂贵对象，并提供统一访问点。

**结构对照（非严格角色映射）**

| 模板角色 | 项目对应 |
| --- | --- |
| `LazySingleton.getInstance()` | Spring 单例 Bean 内部的 `DatasetSeedInitializer.httpClient()` 懒加载字段（仅行为相似） |
| `EagerSingleton`（饿汉） | Spring `@Service` 默认由容器创建并以 singleton scope 管理 |
| 客户端调用 | `AlgorithmController` 构造器注入 `AlgorithmService` |

**模板写法（懒汉）**

```java
public class LazySingleton {
    private static LazySingleton instance;
    private LazySingleton() {}
    public synchronized static LazySingleton getInstance() {
        if (instance == null) { instance = new LazySingleton(); }
        return instance;
    }
}
```

**项目中的相似结构**：`DatasetSeedInitializer.java` 中的 `httpClient()` 对 Bean 字段做延迟初始化。真正保证 `DatasetSeedInitializer` 实例范围的是 Spring 默认 singleton scope；这里不是一个独立的手写单例类：

```java
private HttpClient httpClient;

private HttpClient httpClient() {
    if (httpClient == null) {                       // ← 懒汉式判断
        HttpClient.Builder builder = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(properties.getTimeoutSeconds()));
        InetSocketAddress proxy = resolveProxy();
        if (proxy != null) { builder.proxy(ProxySelector.of(proxy)); }
        httpClient = builder.build();               // ← 首次访问才创建
    }
    return httpClient;
}
```

另外三处「天然单例」：

- `@Service public class AlgorithmService`（`AlgorithmService.java:14`）—— Spring 默认 scope 为 singleton，所有 Controller 共享同一实例，因此**服务层禁止持有请求级可变状态**。
- `@Injectable({ providedIn: 'root' }) export class ApiService`（`api.service.ts:16-19`）—— Angular 根注入器单例，等价于前端全局唯一后端入口。
- `@Injectable({ providedIn: 'root' }) ExperimentContextService`（`experiment-context.service.ts`）—— 靠单例身份在组件树之间共享实验上下文。

> **对照结论**：模板通过私有构造器和静态方法控制实例；本项目由 Spring/Angular 容器管理服务实例。容器托管的单例 Bean 可以持有受控的共享资源，但应避免把请求级可变状态放在共享服务中。

### 2.2 算法分派与静态工厂方法（简单工厂式结构）

**意图**：简单工厂通过统一入口根据类型创建具体产品。本项目有 `ApiResponse.success/error` 这样的静态工厂方法；算法训练中的 `if` 分支则主要负责选择训练函数，并不创建算法对象，因此更准确地说是「简单工厂式的算法分派」。

**结构对照（非严格角色映射）**

| 模板角色 | 项目对应 |
| --- | --- |
| `PenFactory.createPen(PenType)` | `TrainingSimulationService.trainAlgorithmStep(...)` |
| `PenType` 枚举 | 数据库字段 `algorithm.name` / `algorithm.type` |
| `Pen` / `Pencil` / `FountainPen` | `trainLinearRegression` / `trainLogisticRegression` / `trainKMeans` / … |

**模板写法**

```java
public class PenFactory {
    public enum PenType { PENCIL, FOUNTAIN_PEN }
    public static Pen createPen(PenType type) {
        switch (type) {
            case PENCIL:       return new Pencil();
            case FOUNTAIN_PEN: return new FountainPen();
            default: throw new IllegalArgumentException("Unknown pen type");
        }
    }
}
```

**算法分派位置**：`TrainingSimulationService.java:812-846` —— 根据算法名称选择训练函数，结构上类似简单工厂的类型分派，但没有创建并返回统一接口的算法产品：

```java
private StepResult trainAlgorithmStep(Algorithm algorithm, Dataset dataset,
                                      String parameters, ModelData modelData) {
    String name = algorithm.getName() == null ? "" : algorithm.getName();
    String type = algorithm.getType() == null ? "" : algorithm.getType();

    if ("linear_regression".equals(name))            return trainLinearRegression(dataset, parameters, modelData);
    if ("logistic_regression".equals(name))          return trainLogisticRegression(dataset, parameters, modelData);
    if ("kmeans".equals(name) || "clustering".equals(type)) return trainKMeans(dataset, parameters, modelData);
    if ("decision_tree".equals(name))                return trainDecisionTree(dataset, parameters, modelData);
    if ("random_forest".equals(name))                return trainRandomForestStep(dataset, parameters, modelData);
    if ("svm".equals(name))                          return trainSvm(dataset, parameters, modelData);
    if ("classification".equals(type))               return trainLogisticRegression(dataset, parameters, modelData);
    if ("regression".equals(type))                   return trainLinearRegression(dataset, parameters, modelData);
    return evaluateCurrentState(algorithm, dataset, parameters, modelData);   // ← 兜底分支
}
```

同一个类里还有三处同类分派（共 4 个分派位置，并非四个对象工厂）：

- `initializeModelData`（`:673-705`）—— 按算法名创建初始模型数据结构；
- `evaluateCurrentState`（`:847-872`）—— 按算法名选择评估方式；
- `getLossLabel`（`:2832-2851`）—— 按算法名决定损失标签文案。

**另外几处静态工厂方法或类型分派**

| 位置 | 产品 | 形态 |
| --- | --- | --- |
| `ApiResponse.java:8-29` | `ApiResponse<T>` 成功/失败两种结果对象 | 静态工厂方法 `success()` / `error()` |
| `DatasetSeedInitializer.java:200-208` | 合成数据集行列表 | `if ("make_classification") … else if ("make_blobs") …` |
| `learning-guide-data.service.ts` `buildSimulation` | 面板状态 | 按 `algorithm.type` 选 `classification/regression/clustering` 三套指标口径 |

> **对照结论**：算法分派借鉴了简单工厂按类型选择实现的思路，但与 `PenFactory` 的对象创建并不完全同构；静态工厂方法主要体现在 `ApiResponse`。分派逻辑仍存在两个工程质量问题：
> ① 键是裸字符串（`"svm"`），编译器无法校验拼写，改名靠全局搜索；
> ② 四个分派点各写一遍，新增算法必须同步改 4 处，漏一处就出现「能训练但不能评估」。
> 这正是 §5「策略 + 注册表」重构要解决的问题。

### 2.3 适配器（模板 `adapter`）

**意图**：把不兼容的接口/数据形状转换成调用方期望的接口，让老代码或第三方服务能直接接入。

**结构对照（非严格角色映射）**

| 模板角色 | 项目对应 |
| --- | --- |
| `Voltage`（目标接口） | `AlgorithmDTO` / `DatasetDTO` / `ProjectionDTO` / `AiAssistantResponse` |
| `SpecialVoltage`（被适配者） | `Algorithm` 实体、OpenAI 响应 `Map`、YAML 配置项、全维度 `ModelData` |
| `VoltageAdapter`（适配器） | `DatasetService.convertToDTO`、`AiAssistantService.extractContent`、`DatasetSeedProperties`、`TrainingSimulationService.project` |

**模板写法**

```java
public class VoltageAdapter implements Voltage {
    private SpecialVoltage specialVoltage;
    public VoltageAdapter(SpecialVoltage specialVoltage) { this.specialVoltage = specialVoltage; }
    @Override public void supplyVoltage() { specialVoltage.provideSpecialVoltage(); }
}
```

**项目落地 1：实体 → DTO（持久层形状适配成前端形状）**
`DatasetService.java:65-84`

```java
private DatasetDTO convertToDTO(Dataset dataset, boolean withDimensionValues) {
    DatasetDTO dto = new DatasetDTO();
    dto.setId(dataset.getId());
    dto.setName(dataset.getName());
    // …
    List<DatasetDTO.FeatureInfo> features = parseFeatures(dataset.getFeatures());  // JSON 字符串 → 对象
    Projection projection = buildProjection(features);                             // 维度裁剪 → x/y
    dto.setFeatures(projectFeatures(features, projection));
    dto.setDataPoints(projectDataPoints(parseRows(dataset.getDataContent()), projection,
            withDimensionValues ? features : null));                               // 行 MAP → DataPoint
    return dto;
}
```

这里适配了 4 种「不兼容」：JSON 文本 ↔ 强类型对象、任意维度 ↔ 固定 `x/y` 画布坐标、单条记录 ↔ 两种视图（列表精简版 / 详情全维度版，由 `withDimensionValues` 开关控制）、标签列 ↔ `DataPoint.label`。

**项目落地 2：第三方响应 → 内部对象**
`AiAssistantService.java:111-121` —— OpenAI 的 `choices[0].message.content` 嵌套 Map 被压平成 `String`：

```java
private String extractContent(Map response) {
    List choices = (List) response.get("choices");
    if (choices != null && !choices.isEmpty()) {
        Map choice = (Map) choices.get(0);
        Map message = (Map) choice.get("message");
        if (message != null) { return (String) message.get("content"); }
    }
    return "No response received from AI.";
}
```

反向的适配同样存在：`buildUserPrompt`（`:75-109`）把内部的算法/数据集/训练指标对象拼装成 LLM 需要的自然语言 prompt —— 内部模型充当了「被适配者」。

**项目落地 3：配置 → 对象**
`DatasetSeedProperties.java:18-20`，`@ConfigurationProperties(prefix = "dataset-seed")` 把 `application.yml` 的层级键绑定到嵌套 Java 对象（`remoteSources`、`syntheticSamples`），Spring 的 Binder 就是这层适配器。

**项目落地 4：全维模型 → 二维视图**
`TrainingSimulationService.projectModel`（`:177-183`）→ `project(...)`（`:185`）→ `projectRegression / projectLinearBoundary / projectCentroids / projectDecisionTree / projectRandomForest`。同一个「模型」在不同维度组合下要输出不同几何量，这一层把「模型的真实形态」适配成「画布能消费的线/点」。

> **对照结论**：四处都是「接口形态转换」，但项目没有抽出统一的 `Adapter` 接口 —— 对 DTO 场景是合理的（多一层抽象反而增加跳转成本），对第三方 API 场景（AI 服务）则建议补一层 `LlmClient` 接口，以便替换 OpenAI / 本地模型。

### 2.4 观察者（模板 `observer`）

**意图**：主题状态变化时，一次性通知所有已注册观察者，双方无需互相持有具体类型。

**结构对照（非严格角色映射）**

| 模板角色 | 项目对应 |
| --- | --- |
| `Subject`（注册/注销/通知） | RxJS `Observable`（`router.events`、`http.get()` 返回值） |
| `WeatherStation`（具体主题） | Angular `Router` 事件流、`ApiService` 的 HTTP 流 |
| `Observer.update(...)` | 组件 `subscribe(next)` 回调 |
| `CurrentConditionsDisplay` | `ExperimentComponent` / `LearningComponent` |

**模板写法**

```java
public void notifyObservers() {
    for (Observer observer : observers) { observer.update(temperature, humidity, pressure); }
}
```

**项目落地 1：路由事件订阅（`experiment.component.ts:72-78 / 93-97`）**

```typescript
this.navigationSub = this.router.events
  .pipe(filter((event): event is NavigationEnd => event instanceof NavigationEnd))
  .subscribe((event) => {                              // ← Observer.update
    if (event.urlAfterRedirects.split('?')[0].startsWith('/experiment')) {
      setTimeout(() => window.dispatchEvent(new Event('resize')), 60);   // 重算 ECharts 尺寸
    }
  });

ngOnDestroy(): void {
  this.clearTrainingTimer();
  this.navigationSub?.unsubscribe();    // ← removeObserver，等价于模板的 observers.remove(o)
  this.navigationSub = null;
}
```

**项目中的另一处状态恢复：滚动位置还原（`learning.component.ts:182-194`）** —— 同一个事件流有两种事件，`NavigationStart` 时记录位置、`NavigationEnd` 时还原；这更接近页面状态暂存/恢复，不是训练模型的 GoF 备忘录对象。

**项目落地 3：数据链路** —— `ApiService.getDatasets()` 返回 `Observable`（`api.service.ts`），组件订阅后渲染；`forkJoin` 把算法与数据集两个流合并成一个通知。

> **对照结论**：模板手写 `ArrayList<Observer>` + 遍历通知；项目用 RxJS 把「注册/注销/通知/背压/取消」全部内建。**关键差异**是项目显式在 `ngOnDestroy` 里 `unsubscribe` —— Angular 的组件被 `RouteReuseStrategy` 保活（见 §4.5）时不会自动销毁，忘记取消订阅就是内存泄漏 + 重复回调。

### 2.5 代理（模板 `proxy`）

**意图**：为真实对象提供同接口的替身，在调用前后插入额外逻辑（转发、缓存、访问控制）。

**结构对照（非严格角色映射）**

| 模板角色 | 项目对应 |
| --- | --- |
| `HouseRental`（公共接口） | 后端 `/api/**` 契约、`ApiResponse<T>` 外壳 |
| `HouseOwner`（真实对象） | `http://backend:8080` 上的 Spring 控制器 |
| `RealEstateAgent`（代理） | Nginx `location /api/`、MyBatis `@Mapper` 动态代理 |

**模板写法**

```java
public void rent() {
    if (houseOwner == null) { houseOwner = new HouseOwner(property); }   // 按需创建真实对象
    arrangeViewing();                                                    // 附加动作
    houseOwner.rent();                                                   // 转发
}
```

**项目落地**

| 层 | 位置 | 代理类型 | 附加逻辑 |
|---|---|---|---|
| 部署 | `frontend/nginx.conf` `location /api/` | 反向代理 | `proxy_pass http://backend:8080/api/`，顺带解决容器内服务发现与跨域 |
| 开发 | `frontend/proxy.conf.json` | 开发代理 | 把 `localhost:4200/api` 转到 `localhost:8080`，前端代码零改动 |
| 客户端封装 | `services/api.service.ts:18-127` | HTTP API 包装层（非 GoF 代理） | 统一 `baseUrl`、请求路径、参数序列化与响应类型 |
| 持久层 | `repository/*.java` | 动态代理 | MyBatis 为 `@Mapper` 接口在运行时生成实现，业务层看不到 JDBC |

`ApiService` 的封装价值在签名上体现得最清楚 —— 组件只需 `this.apiService.trainStep(id, sessionId, datasetId, params)`，不必关心 URL 拼接、请求体结构和响应类型；但它更适合称为统一 API 客户端，而不是 GoF 代理：

```typescript
trainStep(algorithmId: number, sessionId: number, datasetId: number, parameters: any)
  : Observable<ApiResponse<TrainingSimulationResponse>> {
  return this.http.post<ApiResponse<TrainingSimulationResponse>>(
    `${this.baseUrl}/algorithms/${algorithmId}/step`,
    { sessionId, datasetId, parameters: JSON.stringify(parameters) });
}
```

> **对照结论**：项目中可明确识别的代理主要是 Nginx 反向代理、开发代理配置和 MyBatis Mapper 动态代理；`ApiService` 负责统一封装 HTTP 调用，不应为了凑模式数量而算作代理。若将来要加鉴权、重试和统一错误处理，可考虑 Angular `HttpInterceptor`。

### 2.6 固定流程组织（模板方法式，但非经典 GoF 模板方法）

**经典意图**：父类固定算法骨架（通常由 `final` 方法约束），把可变步骤留给子类实现。本项目的若干服务方法也有固定流程与变化步骤，但没有抽象父类/子类覆写结构，因此只称为「模板方法式流程组织」。

**结构对照（非严格角色映射）**

| 模板角色 | 项目对应 |
|---|---|
| `AbstractClass.TemplateMethod()`（final 骨架） | `DatasetSeedInitializer.run()`；`TrainingSimulationService.stepTraining()` |
| `TakeANumber/QueueUp/Evaluate`（固定步骤） | 「查存在性 → 判是否已满足 → 记日志 → 保存」 |
| `Business()`（抽象变化点） | `fillFromRemote` / `fillSynthetic`；`trainAlgorithmStep` |

**模板写法**

```java
public abstract class AbstractClass {
    public final void TemplateMethod() {
        TakeANumber(); QueueUp(); Business(); Evaluate();
    }
    protected abstract void Business();
}
```

**流程实例 1：数据集填充流程（`DatasetSeedInitializer.java:58-77`）**

骨架固定，只有「获取数据」这一步可变：

```java
public void run(ApplicationArguments args) {              // ← TemplateMethod，不允许子类改写顺序
    for (RemoteSource source : properties.getRemoteSources()) { fillFromRemote(source); }
    for (Map.Entry<String, Integer> e : properties.getSyntheticSamples().entrySet()) {
        fillSynthetic(e.getKey(), e.getValue());
    }
}

private void fillFromRemote(RemoteSource source) {        // ← 变化点 A：真实数据 = 下载 + 解析 CSV
    Dataset dataset = datasetRepository.findByName(source.getName());
    int current = countRows(dataset);
    if (current >= source.getExpectedSamples()) return;   // 固定步骤：幂等判重
    String csv = downloadCsv(source.getUrl());
    saveRows(dataset, parseCsv(csv, ...), name, "下载");   // 固定步骤：统一落库
}

private void fillSynthetic(String name, int samples) {    // ← 变化点 B：合成数据 = 随机生成
    ...
    saveRows(dataset, rows, name, "生成");                 // 同一个收尾步骤
}
```

两个数据来源最终都汇入同一个 `saveRows`（`:254-263`，统一更新 `data_content`/`sample_count`/`feature_count`），体现了固定流程中复用公共收尾步骤的思路。

**流程实例 2：单步训练流程（`TrainingSimulationService.java:87-118`）**

```java
public TrainingSimulationResponse stepTraining(Long algorithmId, Long sessionId, Long datasetId, String parameters) {
    TrainingSession session = requireSession(sessionId);      // 1 取会话
    validateSession(session, algorithmId, datasetId);          // 2 校验归属
    Algorithm algorithm = requireAlgorithm(session.getAlgorithmId());
    Dataset dataset = requireDataset(session.getDatasetId());
    String normalizedParams = normalizeParameters(...);         // 3 归一化参数
    ModelData modelData = readOrInitializeModelData(...);       // 4 取/建模型（备忘录恢复点）
    StepResult stepResult = trainAlgorithmStep(...);            // 5 变化点：按算法训练
    // 6 状态推进 + 7 组装响应 + 8 持久化
    session.setStatus(nextStep >= totalSteps ? "completed" : "training");
    TrainingSimulationResponse response = buildResponse(...);
    trainingSessionRepository.update(session);
    return response;
}
```

`startTraining`（`:50-85`）、`pauseTraining`（`:120-144`）共用「取会话 → 校验 → 组装响应 → 持久化」这条骨架，只是变化点不同：前者多一步「建会话并写第 0 步」，后者**不推进步数只重新评估**。

**流程实例 3：决策树的逐步揭示（`:1033-1049`）** —— 也是一条固定骨架：取树 → 若空则一次建完 → 读 `revealedSplits` → `+1` → `applyTreeState` → 评估。变化点只有「加一」，其余顺序不可乱。

**框架回调机制（不计为业务 GoF 模板方法）** —— `MLPlatformApplication.java` 的 `CommandLineRunner`、`DatasetSeedInitializer` 的 `ApplicationRunner`，以及 Angular 的 `ngOnInit/ngOnChanges/ngOnDestroy`。框架控制回调时机，业务实现回调内容，这属于框架生命周期/扩展点机制。

> **对照结论**：模板库用继承（`abstract class`）实现；项目把固定步骤和变化点放在同一个服务方法及私有方法中，没有经典模板方法的继承结构。更稳妥的表述是「模板方法式流程组织」，而不是项目完整实现了 GoF Template Method。

## 三、框架级使用 / 未使用

### 3.1 框架对象创建机制（不计为项目自建工厂方法）

**意图**：定义创建接口，由子类（具体工厂）决定实例化哪一个产品。

**模板写法**

```java
public abstract class PenFactory { public abstract Pen createPen(); }
```

**项目对应**

| 位置 | 形式 |
|---|---|
| `app.module.ts` `providers` | `{ provide: RouteReuseStrategy, useClass: KeepAliveRouteReuseStrategy }` —— 抽象类 `RouteReuseStrategy` 是产品接口，`useClass` 指定具体实现，Angular 注入器充当具体工厂 |
| `MLPlatformApplication.java:22-53` | `@Bean CommandLineRunner ensureAlgorithms(...)` —— 用工厂方法向容器注册产品，调用方不 `new` |
| `AiAssistantService.java:23-35` | 构造器内 `WebClient.builder()…build()` —— 建造者 + 工厂组合创建不可变客户端 |

> **结论**：项目没有自建经典 GoF `XxxFactory` 工厂方法层。`@Bean`、`useClass` 和 `WebClient.builder()` 分别体现容器注册、依赖注入和建造者式客户端创建，不应简单等同于业务层工厂方法模式。

### 3.2 框架处理链与候选优先级（不认定为项目业务责任链）

**模板结构**：`SensitiveWordFilter.setSuccessor(next)` 串成链，逐个 `doFilter`。

**项目现状**

| 位置 | 说明 |
|---|---|
| Spring MVC `FilterChain` → `DispatcherServlet` → `HandlerInterceptor` → `Controller` | 框架内置链，项目通过 `WebConfig implements WebMvcConfigurer`（`WebConfig.java:7-18`）预留了插入拦截器的位置 |
| `GlobalExceptionHandler`（`config/GlobalExceptionHandler.java:9-24`） | 通过 `@ExceptionHandler` 映射异常类型并返回 400/500；框架负责解析器调用机制，业务代码没有自行实现 successor/handler 责任链 |
| `DatasetSeedInitializer.resolveProxy()`（`:345-358`） | 唯一自建的「候选链」：`DATASET_SEED_PROXY → HTTPS_PROXY → https_proxy → HTTP_PROXY → http_proxy → 配置文件`，用 `firstNonBlank(...)` 顺序取值，命中即返回 |

```java
String fromEnv = firstNonBlank(
        System.getenv("DATASET_SEED_PROXY"),
        System.getenv("HTTPS_PROXY"), System.getenv("https_proxy"),
        System.getenv("HTTP_PROXY"), System.getenv("http_proxy"));
if (fromEnv != null && !fromEnv.isBlank()) { return parseProxyUri(fromEnv); }
```

> **结论**：Spring MVC 内部存在框架级处理链，但项目业务代码没有实现经典责任链。`resolveProxy()` 只是按优先级读取第一个非空配置，没有 successor 指针和 Handler 抽象，不应称为责任链模式。

### 3.3 抽象工厂（模板 `abstractFactory`）—— 未使用，且不建议加

**判断依据**：抽象工厂的价值在于「一个工厂负责同一产品族的多条产品线」，例如模板里 `FountainPenFactory` 同时产 `FountainPen` + `InkBottle`。

本项目只有**一个变化维度**（算法种类）：每个算法对应一个「训练 + 评估 + 初始化」组合，它们属于同一条产品线的不同方法，而不是互相配套的产品族。强行引入抽象工厂只会得到：

```java
// 反面示例：产品族成员之间毫无配套关系，接口纯属噪音
public interface AlgorithmKitFactory {
    StepTrainer createTrainer();
    StepEvaluator createEvaluator();
    ModelInitializer createInitializer();
}
```

**真正的痛点不在「产品族」，而在「分派散落四处」** —— 用 §5 的策略 + 注册表解决即可。

## 四、模板库之外，项目中的模式相似结构

### 4.1 备忘录式快照持久化（Memento-like）

这是本项目**较有辨识度**的模式相似结构，模板库里没有对应目录。

**角色映射**

| 备忘录角色 | 项目对应 |
|---|---|
| `Memento`（快照） | `TrainingSession.modelData` + `TrainingSession.metrics`（JSON 文本，`model/TrainingSession.java:13-14`） |
| `Originator`（原发器，负责存档/读档） | `TrainingSimulationService`（`toJson` / `fromJson`） |
| `Caretaker`（管理者） | `TrainingSessionRepository`（MySQL 持久化，跨进程、跨重启） |

**存档**（`stepTraining` 末尾，`:113-115`）

```java
session.setMetrics(toJson(response.getMetrics()));        // 快照：指标序列
session.setModelData(toJson(response.getModelData()));    // 快照：模型参数/质心/树/边界
trainingSessionRepository.update(session);
```

**读档**（`readOrInitializeModelData`，`:787-811`）

```java
if (session.getModelData() != null && !session.getModelData().isBlank()) {
    return fromJson(session.getModelData(), ModelData.class);   // 有快照就恢复
}
return initializeModelData(algorithm, dataset, session.getParameters());  // 没有就重建
```

**为什么值得单列**：`pauseTraining` 后，模型权重、质心、树已展开分裂数等状态被序列化到 `training_session.model_data`；后续请求通过 `readOrInitializeModelData` 读取快照，再从 `currentStep` 继续。这是备忘录思想的快照持久化实现，但并没有单独封装经典 GoF Memento 对象。

前端的 `KeepAliveRouteReuseStrategy`（`routing/keep-alive-route-reuse.strategy.ts`）也会把 `experiment`、`learn` 两个路由的组件实例保存在 `Map` 中并在返回时复用；这是路由缓存/保活机制，不是训练模型的备忘录对象。

### 4.2 统一服务入口（Facade-like，但不是纯粹的 GoF 外观）

`TrainingSimulationService` 共 **3146 行**、80+ 私有方法，对外只暴露 9 个方法（`startTraining` / `stepTraining` / `pauseTraining` / `getModelData` / `getMetrics` / `projectModel` / `startPca` / `startRandomForest` / `simulateFeatureSelection`）。控制器只看到一个干净的 API：

```java
@PostMapping("/{id}/train")
public ApiResponse<TrainingSimulationResponse> startTraining(@PathVariable Long id,
                                                             @RequestBody TrainingRequest request) {
    return ApiResponse.success(trainingSimulationService.startTraining(
            id, request.getDatasetId(), request.getParameters()));
}
```

门面内部的隐藏复杂度包括：JSON 解析、维度投影、数值归一化、梯度下降、K-Means 迭代、PCA 特征分解、决策树贪心分裂、随机森林 Bootstrap + 投票、SVM 三种核、指标插值、会话持久化。

同类门面还有 `ApiService`（17 个端点收口成 1 个类，全部组件共用一个注入点）、`DatasetService`（把 JSON 文本、维度裁剪、行值装配全部藏在 DTO 转换里）。

> **风险提示**：门面越大，越容易变成「上帝类」。`TrainingSimulationService` 已经同时承担训练、评估、初始化、JSON 序列化、特征解析、投影 6 类职责，建议按 §5 拆分。

### 4.3 数据访问抽象（Repository-like / MyBatis Mapper）

`repository/AlgorithmRepository.java`：接口 + 注解 SQL，业务层只看到方法名，不接触 `SELECT`：

```java
@Mapper
public interface AlgorithmRepository {
    @Select("SELECT * FROM algorithm WHERE name = #{name}")
    Algorithm findByName(String name);
    @Insert("INSERT INTO algorithm (...) VALUES (...)")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    int insert(Algorithm algorithm);
}
```

这是分层架构的数据访问边界：`AlgorithmService` 依赖 Mapper 接口而非直接拼接 SQL，`@MapperScan("com.mlplatform.repository")` 负责扫描注册，MyBatis 在运行时生成 Mapper 实现。它具有 Repository 的隔离意图，但在实现形态上更准确地说是 MyBatis Mapper。

### 4.4 状态（State）—— 训练状态机的轻量实现

`TrainingSession.status` 的取值 `training` / `paused` / `completed` 与迁移规则写在服务层：

```java
session.setStatus(nextStep >= totalSteps ? "completed" : "training");   // stepTraining:107
session.setStatus(currentStep >= totalSteps ? "completed" : "paused");  // pauseTraining:130
```

前端对应 `normalizeStatus`（`experiment.component.ts:643-648`）把字符串收敛为 `TrainingState['status']` 联合类型，编译期即可防止非法状态；`CaseGuidanceState.phase`（`idle/configured/running/verified`）是同一手法在引导流程上的复制。

> **结论**：这是「状态字段 + 条件表达式」，不是 GoF 状态模式（没有 `State` 抽象类与状态对象）。当前只有 3 个状态、迁移规则 2 条，用状态类属于过度设计；**当前实现是合适的**，但状态一旦超过 5 个或出现「暂停中取消」「失败重试」等分支，就该重构为状态对象。

### 4.5 缓存与复用（不等同于 Flyweight 享元模式）

当前可确认的是路由实例缓存、投影结果缓存和 HTTP 客户端复用；这些属于缓存/对象复用机制，不足以单独证明实现了 GoF Flyweight 享元模式：

| 位置 | 缓存内容 | 失效策略 |
|---|---|---|
| `KeepAliveRouteReuseStrategy.handles`（`:18`） | 路由组件实例（`DetachedRouteHandle`） | 进程内长期有效，按 `routeConfig.path` 作键 |
| `VisualizationCanvasComponent`（`viewKey()` / `projection` / `projectionKey` / `projectionVersion`） | 当前会话在当前两个坐标轴上的投影结果 | 键为 `sessionId\|X\|Y`，换轴或换会话即失效；模型每步更新后按 `modelRevision` 重新请求并去重 |
| `DatasetSeedInitializer.httpClient` | HTTP 客户端（连接池、代理配置） | 懒加载一次，进程内复用 |

投影缓存的必要性：用户拖动 X/Y 下拉框时每次都要发请求，而同一组合反复查看是高频操作；缓存 + `projectionVersion` 版本号，既省请求又避免旧响应覆盖新画面。

## 五、重构建议：把 4 处分派收成一个策略注册表

**问题定位**（均在同一文件 `TrainingSimulationService.java`）

| 行号 | 方法 | 职责 |
|---|---|---|
| `673-705` | `initializeModelData` | 按算法名创建初始模型 |
| `812-846` | `trainAlgorithmStep` | 按算法名执行一步训练 |
| `847-872` | `evaluateCurrentState` | 按算法名计算指标 |
| `2832-2851` | `getLossLabel` | 按算法名给出损失标签 |

新增一个算法（例如 `xgboost`）需要改 4 处 `if`。这是典型的「开闭原则」违背：**对扩展不开放，必须改源码**。

**重构方案：策略模式 + 注册表工厂**，形态与模板库 `simpleFactory/PenFactory` 完全一致 —— 区别只是 `Pen` 换成了 `TrainStepStrategy`，`switch` 换成了 `Map` 查表：

```java
// 1) 策略接口：一个算法 = 一个策略实现
public interface TrainStepStrategy {
    String name();                                             // 唯一键，替代裸字符串
    default String lossLabel() { return "Loss"; }
    ModelData initialize(Dataset dataset, String parameters);
    StepResult trainStep(Dataset dataset, String parameters, ModelData modelData);
    StepResult evaluate(Dataset dataset, String parameters, ModelData modelData);
}

// 2) 具体策略：把现有私有方法搬进独立类
@Component
public class KMeansTrainStrategy implements TrainStepStrategy {
    public String name() { return "kmeans"; }
    public String lossLabel() { return "Inertia"; }
    public ModelData initialize(...) { /* 原 initializeModelData 的 kmeans 分支 */ }
    public StepResult trainStep(...) { /* 原 trainKMeans */ }
    public StepResult evaluate(...) { /* 原 evaluateKMeans */ }
}

// 3) 注册表工厂：构造器注入所有策略，按名索引
@Component
public class TrainStepStrategyRegistry {
    private final Map<String, TrainStepStrategy> strategies;

    public TrainStepStrategyRegistry(List<TrainStepStrategy> all) {
        this.strategies = all.stream().collect(Collectors.toMap(TrainStepStrategy::name, s -> s));
    }

    public TrainStepStrategy resolve(Algorithm algorithm) {
        TrainStepStrategy s = strategies.get(algorithm.getName());
        if (s == null) { s = strategies.get(algorithm.getType()); }   // 兼容按 type 归类
        if (s == null) { throw new IllegalArgumentException("No strategy for: " + algorithm.getName()); }
        return s;
    }
}
```

调用方随之退化为一行：

```java
StepResult result = registry.resolve(algorithm).trainStep(dataset, parameters, modelData);
```

**收益对照**

| 维度 | 现状 | 重构后 |
|---|---|---|
| 新增算法 | 改 4 处 `if` + 重启验证 | 新增 1 个 `@Component` 类，容器自动注册 |
| 算法名拼写 | 字符串散落各处 | 集中在 `name()` 一个方法 |
| 单元测试 | 只能整体测 3146 行服务 | 单测单个策略，无需数据库 |
| 类体积 | 3146 行 | 主服务降到约 400 行编排逻辑 |

**不建议动的部分**：`ApiResponse` 静态工厂、`@Mapper` 仓储、`RouteReuseStrategy` 注入、`projectModel` 的几何分派 —— 这些已经是「容器即工厂」「接口即策略」的标准形态，再抽象只会增加跳转层级。
